# SLIM4 platform firmware architecture

- **Boot layer:** Espressif ROM and ESP-IDF second-stage bootloader; OTA rollback enabled in the project defaults. The 64 MiB system A/B and recovery map passes static bounds/alignment checks in `partitions.csv`; target build and image-size fit are still unverified.
- **Hardware self-test (R11):** at every boot, before the drivers start, the GPIO nets are checked (pull resistors, U1 pad joints, shorts); after them the chip, memory, panel (a bounded DSI probe that also keeps a silent panel from hanging the boot), video and power lines. Results go to the log and a page on the panel. They do not decide OTA rollback: a hardware fault is not the image's fault.
- **Bring-up console (R12):** a command console on the USB-C port (USB-Serial-JTAG, the primary console) starts right after the GPIO checks, before any driver. It reads pins, power and the panel probe, sets the backlight, holds test patterns on the panel, plays tones on one side and chooses the DSI profile (safe by default, inside the panel's limits). With no terminal attached it drops output rather than wait.
- **Update service:** `slim4_system_update` streams an image into the inactive OTA slot, lets ESP-IDF validate it, selects it for next boot and preserves the factory recovery image. The next boot tests display initialization and controls before confirming the candidate; a failed software self-test requests rollback.
- **System firmware:** the R23 BSP owns the physical GPIO, display, audio, power and NVS access. The current diagnostic build initializes the Crystalfontz CFAF7201280A0-050TN (ILI9881C, two-lane DSI), runs a full-frame color/sweep update at a 60 Hz target, reads and counts four buttons, and queues channel-specific speaker tones. It changes the boot stamp to `VERIFIED` only after software-level input/display checks pass. A USB update service is not implemented.
- **Platform API:** versioned C interface provides fixed-step game timing, debounced controls, RGB565 framebuffer, queued stereo PCM, pause/resume and per-game save blobs.
- **Games:** linked as application modules for this first milestone. API ownership is separate so a future launcher/package loader can replace the selected game without changing the board drivers.
- **Audio:** standard 16-bit stereo I²S, no MCLK, on GPIO5/6/7. A dedicated worker drains the PCM queue. GPIO8 plus the board's resistor ladder enables both MAX98357A amplifiers while selecting separate left and right slots.
- **Radio:** no Wi-Fi or Bluetooth services are included. Updates/recovery are intended to use USB/service mode after board USB role is verified.

The system boot path, hardware diagnostic loop, game API, R23 display/input/power and stereo I²S paths, save namespacing, and A/B image writer are implemented and build with ESP-IDF v6.1; they are not yet tested on assembled hardware. Diagnostic draw FPS counts firmware submissions; a separate counter reads the P4 DPI VSYNC callback, which confirms controller timing events but cannot optically verify panel output. USB update transport, launcher, game loader, and cryptographic update authentication remain unimplemented. Display output and left/right speaker mapping are bench tests (`FIRST_BOOT.md`). The panel's pin table and init sequence are the vendor's, and J1 is checked pin for pin against the pin table.
