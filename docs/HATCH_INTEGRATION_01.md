# HATCH INTEGRATION 01

November 4, 2026 · UTC

Complete checkpoint over SERVICE-01. This is the fourth and final estimated cloud development pass: focused integration and debugging across the completed HATCH slices. It integrates the accepted capability-launcher role into Hatch, closes the remaining per-category settings audit, repairs the service-cycle, Operations, installer and startup readback that the integration review found untruthful or fragile, and makes the shipped release check follow the HATCH checkpoint instead of failing on a historical comparison. Nothing here is native, HATCH, I05, I06 or owner-host acceptance.

## Hatch as the capability launcher

Hatch keeps its five original choices first: New Idea, New Project, On, Off and Reboot, with the same action objects, order and service routes. Below them a Services line shows the current service summary and opens the existing Background service room. Six capability groups follow: Work, Reason, Instruments, Programs, Knowledge and Configuration. Each row is one of the presentation adapters behind the existing read-only ledger.explore projection over the capability catalogue; the catalogue, the adapters and the workspace factories are the same ones Explore uses, and Explore the workshop… remains the broad discovery route. A separator and the session footer close the menu. Every entry is created once, so positions and identities are stable; opening the menu refills only the group submenus.

One service refresh and one ledger.explore read happen when the menu opens, and the menu holds still while it is open. The one-second service timer never reads the catalogue. Opening a row is navigation only: it goes through the existing open_instrument route, which rechecks availability and opens the original factory inside a retained view. Hatch dispatches no operation other than the read ledger.explore. If that read fails, the groups are hidden and one disabled row carries the message; the five choices, the Services line and the footer keep working.

A row shows only what was observed. Its text is the adapter title plus, in this order and only when true: unavailable (the row is then disabled), open, N running, N queued, N interrupted, and for the local model ready, stopped or no model selected. Its tooltip gives the description, the view state and tool prerequisite state, the owner's own job counts, the local-model state, the sentence "Qualification: not assessed on this host. Opening runs no tool." and the room statement below. Registration counts are never shown. The words mean exactly this:

| shown | asserts | does not assert |
| --- | --- | --- |
| row enabled | every module the route opens is present and the family has registered operations | that the view renders without error |
| unavailable | a required adapter module is missing or unsafe, named in the tooltip | — |
| Tools: Use existing controls | no job tool has this prefix | — |
| Tools: Not assessed | job tools exist without a native profile | readiness |
| Tools: Detected · checks remain | an executable was found on PATH or a pinned archive verified; version unmeasured | that it runs |
| Tools: Needs setup: a, b | passive discovery failed for the named executables or runtimes | — |
| N running / queued | the owner's durable job records in those states, bounded | live processes |
| N interrupted | the owner's job records in the Interrupted state | — |
| open | a center tab of that workspace class exists | that it belongs to the selected record |
| ready / stopped / no model selected | the local-model status: ready means the owned worker's process identity matches the selection | quality or context occupancy |
| Services · summary | the service-cycle snapshot summary; admission and confirmed stop stay distinct | that services are stopped when new work is merely held |

Six presentation adapters were added for the native tool families that already had tabs, navigation routes and passive detection: KiCad, KiBot, ngspice, Yosys, nextpnr & Trellis and HDL simulation. They form the Programs group, which is what makes "installed programs" a truthful part of the launcher: their readiness words come from the catalogue's existing passive detection, nothing is executed by opening a row, and version and licence stay unmeasured. In this container none of the executables is present, so each Programs row's tooltip reads Tools: Needs setup with the missing programs named (the row text itself carries only the title and the observed suffixes); on a host with the tools installed the same tooltips read Detected · checks remain. KiCad without an attached project shows the existing project-required dialog and says so in its tooltip. The adapter count is 21. Activity & receipts now opens the Work trail room, a real center tab, instead of returning the activity strip; Calculate & compare and Laboratory now require every module their route actually opens before they read as available; interrupted jobs are counted separately instead of disappearing from the counts.

Three defects in the shared Explore code were fixed on the way: the Explore button created five new submenus on every opening and never deleted them; the Explore tab left its result list disabled after a failed refresh; and a second New Idea stacked a second capture sheet instead of raising the visible one (closed sheets are now released as well). Group submenus now show their tooltips, which they never did. Both menus read the local-model state the same guarded way, so the same stored state gives the same word in Hatch and in Explore, and the word "state unavailable" appears only when the read actually failed. The catalogue read caches file digests by path, size, modification time, change time and inode, so a menu opening costs about 0.08 s here instead of 0.17 s; any change to the file recomputes. While the menu is open a service transition changes tooltips only; the Services line and the popup geometry hold still until the next opening, and a summary too long for the line is carried in full by its tooltip.

## Session footer decision

The footer has one live item and three items shown unavailable. The live item reads Return to Debian when the program runs under LS_XSESSION.sh, which now exports ARC_LEDGER_XSESSION=1, and Exit Ledger from an existing desktop or Windows, where no session of Ledger's own ends. It opens the existing Leave Ledger & Slate? review, whose default is Continue working, and then the ordinary close: Save or Discard for each modified editor, the return copy, local model and tracked command shutdown, session save and lease release. In the dedicated session the X session then ends and the Debian text login returns; the computer stays on, and START_MINIMAL_DEBIAN.sh reports the exit status Ledger recorded. A service cycle in progress is recorded as interrupted, and the tooltip says so while a cycle is draining or stopping; Hatch → Off remains the graceful service stop.

Log Out, Restart Computer and Shut Down Computer are present so the footer keeps the shape the owner asked for, but they are disabled with a tooltip that says Ledger never logs out, restarts or powers off the computer and points to the console after Return to Debian. The reasons are recorded here: Hatch issues no operating-system session or power command (a hard boundary of this product); the dedicated session has no session manager, so logging out of a text login is the console's own exit; logind and polkit rights are unqualified on the owner host; Reboot already means Ledger services and a live Restart Computer beside it would make the word ambiguous; a power command would bypass the save prompts. The Hatch module imports no process facility and a test greps its source for one; the Qt check holds subprocess, os.system and QProcess.startDetached while every footer action is triggered.

The test the Interface Companion asked for: LS_XSESSION.sh runs START_OFFICE.sh once in the foreground, propagates Ledger's exit status, and its exit trap ends the window manager; no loop, unit, autologin or xinitrc restarts Ledger. A shell test with stubbed window manager and Office demonstrates it for exit statuses 0 and 3. This is a test result on this container, not owner-host acceptance of the minimal Debian startup, which stays open.

## Rooms by entrance and Off when already off

Workspaces opened from Hatch or Explore are retained rooms: inserted at the left, never replacing the edited source Preview, not counted among the five pins. The same workspace class opened from a top menu is a Preview or pin as before. This asymmetry protects the Preview on the most common entrance; it is now stated in the row tooltips, in the Pin tooltip and here.

Off is disabled while the recorded phase is already OFF, with a tooltip that says services are already off and On enables new work. This is a deliberate tightening of the Hatch enable rule: a second Off used to record a redundant cycle and two more journal entries without any observable change. The conservative rules for On during draining and stopping are unchanged.

## Service cycles and Operations readback

The service snapshot now reads only non-terminal job rows, so finished work no longer costs a process-identity probe per record every second; with three hundred completed records carrying exited worker identities the one-second drain costs about two milliseconds instead of seconds. Paused agenda and idle-study timers restart after a failed or interrupted cycle and whenever admission is observed enabled again, so a Settings re-enable followed by Resume no longer strands them until a restart. A corrupt or partial cycle row makes the service status unavailable without taking down the Operations queue, raising from the timer every second or repeating the status message every tick; the cycle row is validated field by field when read. A failure after a successful start no longer downgrades a completed cycle to incomplete; the restore request runs in its own guarded step and records its own failure. Save cancelled or save failed before a cycle is reported as "not started" rather than as an incomplete cycle. The hold message names running records that have no live worker. The service details room says observed running once an owned worker is seen for the requested model, and request failed when the request's job ended without completing. The On note no longer asserts phone state it did not observe. The lifecycle driver is stopped and joined when the window closes. Tracebacks are logged where the driver has to swallow an exception to fail a cycle. The ledger.operations result keeps every key; an unreadable cycle row now yields an unavailable services block instead of a failed read.

## Settings: the hardware category views

hardware.category_views is the forty-first genuine setting. It is the existing per-pane Auto view / Details / Thumbnails preference of the hardware overview, stored in the same connected-profile field it always used, with the same value shape and no migration. It appears under Ledger → Workspace → Hardware with its own map editor, is written through the single-key ledger.settings.set route with the row revision, and is read back map-aware: no open pane, applied when every open pane shows the saved mode, pending desktop otherwise. The panes write only on an explicit change, never on refresh, and follow an outside change (Slate, the editor, Undo, Default) without a second journal entry. The seventeen-key batch contract is unchanged and rejects the new key, as it rejects favorites. The forty prior definitions are byte-identical to SERVICE-01, proven by a text comparison in the tests; the operation registry digest is unchanged because settings are not part of it.

Profiles written before this pass carry an explicit Auto view entry for every pane that was ever visited; the editor round-trips those entries unchanged, so opening it is never an unsaved edit, and the summary counts only panes that are not at Auto view as customized. A refused pane save returns the pane to the saved mode so the readback stays applied rather than pending.

The remaining audit is closed in docs/SETTINGS_INVENTORY_06.md. The Orange Book automatic-update switch is the one other genuine preference found; it is explicitly retained in its original control with its reason recorded. Four connected-profile fields that were written but never restored (library sections, typing target, console mode and history, pill link) now have bounded loaders, and the console history is capped. The companion overlay's position fields are classified as live workspace state, correcting the earlier "retired" wording. Settings robustness was improved alongside: a corrupt priority file or a tampered Kernel-table row reads as a store-unavailable row that Default can repair instead of failing the whole settings read (a file the program cannot read at all is reported without that promise), Kernel-table values are validated on read, orphaned journal rows no longer break history, stale consumer receipts are pruned, and the visual-versus-policy readback rule is derived from each definition's store instead of a key list.

## Startup and installation truth

INSTALL_LS.py never prints a bare "Installed." again. Its final line names what happened: program extracted and verified, runtime imports verified, Debian prerequisites installed or skipped with the reason, minimal-session prerequisites present or missing, and that owner display and native or model qualification remain separate. It passes --yes to the Debian installer only when given, says beforehand when no terminal is attached, and reads INSTALL_DEBIAN.sh's new exit status 3 (PREREQUISITES_SKIPPED) honestly. Chunk metadata in RELEASE_PARTS.json is validated before anything is written, unreferenced chunk files are refused, a write-only chunk mode is refused and a missing mode falls back to ordinary file permissions, an unwritable containing folder is named before staging, an empty parent chain created by a failed run is removed, and every failure reads "Installation needs attention". --plan --extract-only lists the one step it performs and no start command. The restored tree from the SERVICE-01 media was compared file by file with the pristine tree after the change: identical.

LS_XSESSION.sh exports the session marker the footer reads and records Ledger's exit status in last-session.json under the state directory; START_MINIMAL_DEBIAN.sh reads it after startx returns, prints "Ledger ended with status N" with the error log path when one exists, and exits with that status instead of startx's constant zero. It refuses arguments in the dedicated-session branch (they only work from an existing display), and it checks for an X server binary as well as startx, Fluxbox and the session bus. INSTALL_LEDGER.sh --quick prints the dedicated-session start line only when those commands are present. The launcher names its error log only after writing it and uses the product name in its alert. tools/package_release_parts.py now takes the checkpoint name as a required argument and places the start-here documents in the first volume. docs/MINIMAL_DEBIAN_INSTALL_01.md records all of it, including that --manifest-sha256 also pins copied USB media.

## Shipped checks and documentation

tools/check_release.py now routes by the manifest's hatch_checkpoint to tools/check_hatch.py. The new checker verifies the runtime payload and source bindings, compares the live registry against docs/HATCH_SERVICE_01_CAPABILITIES.json (generated in this pass from the unmodified SERVICE-01 tree, as its note says), compares the forty baseline setting definitions byte for byte, admits additions only when the checkpoint's RESULT records them, and reports the historical I04 comparison with its three documented additive extensions by name (work.investigate from I05, the ledger.navigate destination enum from ATLAS-01, ATLAS-02 and DISCOVERY-01, and ledger.settings.set's optional expected_revision from SETTINGS-01) instead of failing on the first of them. Its self-test runs a defined list of focused modules one by one and never a discovery over the whole folder. It states that registration counts and passing checks are not readiness or acceptance.

The four historical test failures were repaired: three stale literal settings counts now derive from the registry, and one historical module imports its fixtures by package path when run per module. The five historical Qt tools that aborted on stale literal counts or on the pre-cabinet navigator run again. README.md and GETTING_STARTED.md carry an INTEGRATION-01 banner with the current numbers above their historical layers and describe the shipped check as it now behaves; the six stage suites are listed as historical suites, four of which report documented additive schema extensions.

Definitions used in this document and its receipts: unchanged means identical bytes or schema; retained means still present, possibly different; extended means an additive schema change listed explicitly; added means a new definition recorded in the RESULT.

## Review before packaging

Every work item was reviewed by independent readers under three lenses before packaging: the hard boundaries (registry, settings, dispatcher, operating-system commands, fixed desktop controls, held launchers, historical evidence, acceptance words), correctness, and truthful readback. The readers returned thirty-one candidate findings, each with a path, a probe or a command; none was a boundary violation. Twenty-nine were real or cheap enough to fix and are fixed in this checkpoint (among them the Explore local-model word, the legacy Auto view entries in the new editor, the FAT-media installer message, the job-tool comparison and the legacy flags of the new checker, and captions that described tooltip text as if it were rendered); two were wording and were reworded. The service-cycle driver and the installer scripts were read line by line by the integrator as well.
