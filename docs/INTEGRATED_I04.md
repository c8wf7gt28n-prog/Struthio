I04 meets its execution-host reference acceptance family. The 35 focused tests and coordinator checks pass. ThinkPad and broader unseen-task qualification remain I06 work.

## Use the investigation workspace

Install the full program as before. The I02 math and I03 experiment dependencies remain optional; no model weights are bundled or silently downloaded. Register and start an owner-selected GGUF in Brain. The existing pinned CPU runtime, authenticated loopback, template/tokenizer checks, model-file identity and resource guard remain in use. I04 admits the `qwen35` architecture to the read-only inspector's trial list; actual native loading/generation and task performance are still separately tested.

The frozen model configuration includes resident weight loading through the pinned runtime's `--load-mode none` option. The selected native address-space limit and host-memory preflight remain enforced. A successful load is separate from task acceptance.

Open Project Desk → Problem sheet → Investigate → Slate investigation. Reopen or create the problem with its known quantities, explicit unknowns and delegated working copies.

1. Select **Read and calculate** or **Working-copy tools**, review the step/time/token limits and click **Prepare investigation**. Preparation freezes the selected operations, copy identities, assignment, initial problem revision, model configuration and executor/schema bindings. It executes no tool or model decision.
2. Inspect the displayed scope and click **Start with this scope**. This uses the existing owner-grant mechanism once. Slate can make adaptive choices within that scope; it cannot add operations, copies, effects or resources to its grant.
3. The current uncertainty and predicted distinguishing outcomes appear above the frontier. They are Slate's proposals. The observation table shows actual completed operations, adverse outcomes and failures separately.
4. A consequential missing-input question pauses the investigation. Enter the requested half-open lifetime intervals and their time units, state their basis, and click **Supply these lifetimes**. These are owner-supplied inputs, not measured hardware facts. They create a new problem revision before another decision can use them.
5. Inspect retained alternatives, rejected/refined branches and the proposed finding. Right-click an observation for its actual receipt and the question it addressed. Use Pause, Resume or Revoke; the existing master Stop also retains its authority.

The **Direct response allowed** profile permits a response that needs no experiment. The default investigation profile requires actual current-context observations before a finding can finish. A model's text alone does not satisfy that policy. A proposed finding still requires review for interpretation and completeness.

## Exact instruments

`math.concurrent` compares the sum of selected saved scalar allocations against a saved capacity under an explicit concurrency assumption. The model supplies variable names, not copied numeric values. The existing exact IR, units, source bindings and durable math action/result records perform the calculation. It does not need lifetime values and does not imply that actual allocations overlap.

The ACTION argument grammar enumerates declared known quantity and lifetime names for these instruments. The model still selects the capacity, allocations and pairings. Numeric values or JSON interval values cannot masquerade as source names. The registered public tools retain their own complete input validation.

`math.calculate` offers the existing expression/solver profile as one source-bound call. The adaptive fragment requires saved variable names so that units and source identity survive the expression. A quantity result is not a constraint check. Literal-only calculations remain available in the existing calculator's own profile; they are not admitted as source-bound adaptive calculations.

`math.schedule` performs an exact rational sweep over explicitly supplied half-open `[start, stop)` intervals. Releases at a boundary occur before allocations there. It records selected quantities/lifetimes, peak demand, segment demands, capacity and assumptions. Missing lifetimes return UNKNOWN; they never become zero. Time units are converted exactly, allocations and capacity must share dimensions, and negative or empty/reversed lifetimes are rejected. The model cannot supply guessed lifetime values through this operation.

The adaptive schedule fragment waits until the declared lifetime inputs are known. Tool readiness can change when the owner supplies inputs; the original grant does not grow. The underlying public schedule API can report unknown selected lifetimes independently.

The scheduling model is additive. It does not model fragmentation, alignment, allocator overhead or indivisibility. It can establish a consequence of the supplied intervals and amounts, not a physical memory guarantee. The generic resource dimension supports later structural-transfer work, whose method/precondition qualification belongs to I05.

New math receipts remain in the existing owner-scoped Project Desk store. No mathematical source or model text can self-assign a passing hardware qualification.

## Separate ACTION profile

The legacy `slate.ask` tasks and PLAN allowlist are unchanged. PLAN still proposes read-only calls and does not execute them. ACTION uses the new `brain.action` job and current granted operation catalogue.

ACTION inference has two bounded phases. SELECT chooses a currently available operation, candidate key, uncertainty and expected distinguishing outcomes. ARGUMENTS fills that operation's schema and proposes any branch updates. Both are real model generations; the coordinator validates the complete assembled response before any action is executable. Neither a partial stream nor either phase by itself is an action.

SELECT explicitly presents ASK and FINISH alongside the tools. FINISH reports a conditional finding once current receipts resolve the full request and requested follow-ups. The model chooses when to use it; the controller does not replace a duplicate call with a fabricated final answer. Repeated unchanged calls still stop visibly.

The coordinator inserts fixed problem/revision bindings, reconstructs the complete registered call and validates its schema again. Copy IDs must belong to the grant. A native action must have been prepared by this same work order before it can launch. Result reads cannot select unrelated jobs or calculations. Working-copy application can use only a proposal created by this work order, with the existing exact proposal digest and change journal.

The prompt contains bounded source/current-problem data, current tool readiness, retained observation summaries, proposed alternatives and the remaining limits. SELECT sees tool descriptions and readiness; ARGUMENTS sees the selected tool's complete argument schema. Both phases see the actual observations. The full source/model/frame binding remains in the immutable request and is validated before and after inference. Completed operations and remaining unknowns are explicit feedback. Actual tool results are data, and source text cannot change permissions. Predictions and candidate explanations remain model proposals. JSON/schema validation does not prove the semantic truth of a model's interpretation.

Original-file publication, arbitrary host commands, installation, new grants and general scheduler mutation are outside this adaptive catalogue. The selected working copies retain their own read/write/execute policies and registered native profiles. I03's bounded standard-library Python execution and native KiCad/Office profiles remain separate instruments.

## One executor, durable checkpoints

Adaptive work uses the existing `flow_orders`, grants, steps, events and Agenda rows. No new scheduler, background timer, database schema or generic record-writing API is introduced. The new work profile freezes a catalogue and scope; the selected steps are added as the investigation proceeds. The legacy profile still freezes exact calls in advance.

The grant binds the operations, effects, copies, budgets, expiry, model configuration and executor/schema identity. Each branch and observation points to its problem revision/context. Owner answers create a new revision; earlier observations and branches remain historical. Current findings cannot cite stale-context results as their current support.

New actions select an active current branch. Historical and rejected branches remain available for inspection and properly cited interpretation, but cannot silently become the next active branch. The owner-answer revision introduces a current branch for the supplied inputs.

Before an action, a durable intent reserves its resources and identifies the step. A native model/application job receives a stable request key. The next decision waits for the actual completed/failed job result; a launched process never stands in for an observation. Registered result adapters validate their own files, exit status and schema/units. The coordinator records an immutable actual-observation digest in the existing record store and links it to the work step.

Adverse results and tool failures differ. A false checked constraint can support rejecting/refining a candidate for that recorded case. A timeout, parser error, missing dependency or cancelled job cannot refute the hypothesis. Rejection proposals must cite an actual adverse observation in the branch's context. The existing I03 four-valued evidence/reason views remain available; adaptive frontier status is not a new proof system or reviewed-fact authority.

Before continuing after a newly adverse observation, the complete ACTION proposal must include a cited branch interpretation. The model chooses REJECT, REFINE or RETAIN and supplies its reason. The coordinator does not choose that disposition or certify the reason's meaning. A response cannot reject a branch and simultaneously select that branch as its next active action.

Each action and observation retains the branch that the model selected to test. Required feedback addresses that tested branch. Updating a different explanation cannot silently count as interpreting the failed check. Citation lists are bounded by the available owned observations and reject duplicate entries.

ACTION uses its own strict, dependency-free schema-subset validator, including exact union selection, array bounds, unique citations and identifier patterns. Unsupported schema keywords stop validation. This validation runs independently after generation and again on reconstructed tool calls. The legacy PLAN implementation and allowlist remain unchanged.

Step, active-time, token, frontier, decision, failure, working-file and retained-observation limits are explicit. The model's fixed native memory budget must fit the work grant. Child tools retain their own execution/resource profiles. Controller retained-output accounting is distinct from native artifact limits, and the model's address-space limit is not a new aggregate cgroup guarantee for the whole desktop.

Unchanged duplicate calls stop with a recorded stall reason. Exhausted branches, changed inputs, incompatible executor/model versions, missing dependencies and exhausted budgets stop or wait visibly. The controller does not silently extend a grant, fill missing input or keep retrying indefinitely.

Reopening a record performs no automatic investigation step. An interrupted in-flight step is reconciled under the existing Agenda lock and requires explicit Resume. A completed working-copy application is recovered from the existing Changes journal; it is not applied twice. Uncertain partial applications require Changes recovery. Interrupted reads/calculations can repeat only after explicit resumption, with their reservations retained. Source/copy/model versions are checked again.

Pausing or revoking work cancels its pending owned job where applicable. Progress commits recheck the grant, epoch and current step so that a late result cannot overwrite a pause/revocation. A completed proposal is never authority to continue after its grant changes.

An owner lifetime answer writes the problem history and investigation checkpoint in one Kernel transaction. An interrupted answer preserves the old revision and pending question. The retry can commit one new coherent revision. Owner controls are checked again before a new intent, while collecting failed model jobs, during explicit resume and before reconciliation commits.
