## What the owner's direction changed

Commission v2.1 governs where it conflicts with the earlier specification's prescriptions: effort goes to implementation; checks are focused smoke checks of changed behaviour rather than sweeps; the gate order is a working order. The specification's decision register still supersedes four rules earlier checkpoints had built to, and this pass follows the newer decisions: Hatch is the primary doorway to usable tools and the five-choice first-item order is history; the machine overview and the Slate activity column stay visible beside the centre, so Home no longer hides the right column; the side columns are no longer forced to one width by a hidden-label ratchet; the left column is a machine and work navigator rather than only an office cabinet. Capabilities, records, routes and action identities are preserved while their presentation changes. Menu words, palette values, the X marker and priority labels remain provisional, reversible defaults for owner review (PD04).

## The permanent five parts (UI01, UI02, LP01)

The left column, the centre, the right column, the Ledger Head and the typing strip stay visible together. Home keeps the right column; Today sits in the centre. Each side column has its own two-way minimum derived from its own row of words (the left from Hatch, Explore and the console sizes; the right from the typing targets), scaled with the interface size; when the need shrinks and the column sat on the old minimum it comes back down; an owner-dragged width survives; both widths are remembered through the connected profile (layout.navigator_width and layout.simulator_width), and the saved widths reach the desktop at start. ## Hatch as the tool doorway (HT01, HT02, HT03)

The capability groups come first: Work, Reason, Instruments, Programs, Knowledge and Configuration, then Explore the workshop…; below them New Idea and New Project; then the Services line (opens Service details) and a Ledger services submenu holding the existing On, Off and Reboot actions with their routes, identities and rules unchanged; then the live exit item (Return to Debian in the dedicated session, Exit Ledger elsewhere) and one disabled row for Log Out, Restart and Shut Down that carries the reasons in its tooltip. Every entry is created once; opening the menu refills only the groups; the menu holds still while open. At 14 pt the menu is 411 by 521 px and fits 1366 by 768 and 1280 by 720 in one column; at 18 pt it is 522 by 625 px and still one column.

Each row publishes its actual route, as the capability presentation contract asks: what opens (a Ledger-built workspace, Ledger's checks for a native tool, or application operations), what Slate can do there (the registered family operations with their scopes, six shown and the rest counted), what is missing (the executables passive detection did not find), the qualification state (not assessed on this host) and the current work context. The native-tool rows are named for what they open: KiCad checks, KiBot outputs, ngspice profiles, Yosys synthesis, nextpnr & Trellis, HDL simulation checks; none implies that the complete editor has appeared. Needs setup appears in the row text itself, not only on hover; a KiCad row without an attached project opens the existing project-required explanation, as its tooltip says. Opening a row is navigation; discovery starts no model, native tool, calculation or worker. Keyboard users open Hatch with Space or Enter, move with the arrows (Up from the first row wraps to the exit item, past the disabled power row), and read a highlighted row's descriptor with F1 or Shift F1 in the typing-strip note. The Explore word keeps the record suggestions, Explore the workshop… and Find saved work; the groups are listed in Hatch only. Work gains a Documents row.

## The shared document (WS01, WS02, CM02, CM03, AI03 in part; AC03 and AC09 mechanically)

Hatch ▸ Work ▸ Documents opens a page in the centre: a Ledger-native document stored as a Project Desk record (kind document, schema ledger.document/1: a title and paragraphs with a style and inline bold, italic and underline marks), edited in a QTextEdit in the prose font with a marks row of pink action words and the usual keys. The page saves itself 1.5 s after typing pauses, when focus leaves it, on Ctrl S and before any Slate request, always against the revision it last saw; an unnamed page is called by its first words. The owner selects words, moves to the strip and asks Slate in plain words; `documents.interpret` resolves formatting requests by explicit rules (bold, italic, underline and their removal, heading levels, body, code, plain, replace x with y; undo and redo work the page's own stack) and anything else is left to the model path with the document and selection as context. A recognised request becomes `documents.edit`, which names the block, the offsets and the quoted words against the expected revision and refuses a stale revision or changed words; the change lands as a revision by SLATE and is applied to the page through the same undo stack as the owner's typing, so Ctrl Z takes Slate's change back like any other. The answer in the right column names the change, the revision, that no model was needed and how to take it back. With no model selected Slate says so and lists the direct edits he can still make. Reopening a page (from the list, the cabinet's Documents folder or the action shelf) reads the saved revision; Export… writes Markdown, HTML or plain text. Seven operations are added and recorded (documents.create, save, edit as execute; list, get, interpret, render as read); documents.* is private to this computer for cloud proposals; the ledger.navigate destination enum gains documents (recorded extension). The live-model turn, takeover and resume, other artifact kinds and a DOCX export remain open.

## The model's small tool set (Commission v2.1, first step of the agent loop)

When a request goes to a loaded local model in plan mode, `workbench/tool_selection.py` chooses up to six registered operations for the request's words by explicit matching over operation names, the capability families of the Hatch adapters (titles, descriptions, keywords, plus Machine, Notes, Mathematics and Agenda) and argument names; each comes with a one-line reason, and only read and execute operations are offered. The plan schema keeps its fixed direct set (now including documents.get and documents.edit) and adds the chosen contracts, so a 4B model reads a handful of relevant schemas instead of the registry. The owner still reviews and runs every proposal. This is untested with a live model here; `tests_integrated/test_tool_selection.py` covers the selection and the schema mechanically.
