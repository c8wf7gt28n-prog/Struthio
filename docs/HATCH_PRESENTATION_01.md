## Favorites with a visible home

Settings → Ledger → Favorites offers Work, Revise, Arrange, Tools and Guide. Each group has three ordered selectors using the original command labels. No favorite is a deliberate empty slot; an empty group stays empty. Apply validates the original eligible IDs, at most three choices and no repeated command within a group. Invalid and stale drafts remain available. Default and Undo use the same shared history as the other settings.

The canonical keys are favorites.file, favorites.edit, favorites.view, favorites.options and favorites.help. Their backing values are the existing Session toolbar_favorites groups File, Edit, View, Options and Help. Serialization IDs and group keys remain stable even where the current shell uses different visible words. The single-key Set route is shared by the legacy customize control, typed Slate and Settings. The original public batch contract remains restricted to its previous 17 Session keys; its schema has not expanded.

Commands → Favorite commands makes the saved choices useful in the paper shell. The menu adds the original QAction objects, preserving their shortcuts, enabled states, checks and command routes. Opening the menu does not trigger them. A command saved in two groups appears once in the combined menu, without rewriting either group. Membership refreshes before opening; a visible menu keeps its membership until it closes. The retired icon strip stays hidden.

A version-two marker distinguishes explicit current choices from old factory groups. Reading an old profile does not rewrite its bytes. Pre-versioned exact old factory groups retain their previous migration behavior. The first explicit favorite write normalizes the other legacy groups once, then records literal version-two choices. Selecting a group that happens to match an old factory group now remains intentional rather than silently being migrated again. Unknown IDs never become callable commands.

## Existing views without changing filing

Settings → Ledger → Cabinet → Existing catalogue view adapts preferences.view in the original connected Concern catalogue. Choices retain their existing IDs: works, offices, work and archive. The editor shows Properties & works, Offices, Work & ideas and Archive. The setting is scoped to that connected personal catalogue profile, which can be shared by different workspace journals. It does not move records, change source authority, rename identities or choose logical cabinet parentage.

The existing view chooser journals the same setting. Consumer synchronization updates its hidden selector, the visible Showing sentence and the original catalogue tree. A consumer-driven selector update does not write the setting again. The logical cabinet's saved selection and expansion remain intact; existing per-view expansion behavior is retained.

The optional store is read without initialization. Missing, corrupt or unsupported catalogue data marks this setting unavailable while other settings remain usable. A Set cannot create a replacement catalogue. The original SDK view setter and the shared adapter both stamp an opaque revision in the catalogue transaction, including same-value writes. Shared writes recheck that stamp at the actual SQLite write, so another workspace or a legacy chooser changing away and back still invalidates a stale draft and Undo.

## Delivery and readback

Session favorites retain the existing locked-profile delivery and journal recovery path. Catalogue and Kernel history are separate SQLite stores: there is no claim of one cross-database atomic commit. A private delivery receipt is written before the external catalogue change; the value and new stamp commit together in the catalogue, then the shared journal commits. Recovery records an interrupted delivered change only when its exact value and opaque stamp match. A before-write failure is not recovered as applied. A later conflicting change, disconnected catalogue or unavailable store is retained for review. Recovery never blindly replays a preference.

Settings distinguishes saved policy from desktop application. Favorites require a live matching desktop receipt. Catalogue application requires the original Existing views consumer. With no live consumer, effective remains unobserved. No model, provider, process-priority change or engineering job is launched by these settings.
